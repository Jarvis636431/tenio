# A.PM 智管 核心功能流转逻辑总览

## 1. 账号与短信登录逻辑

**功能描述：**
用户的邮箱字段已弃用，手机号即为可用于登录的用户账号（Account）。用户首次进入系统必须使用手机号与短信验证码进行验证（相当于注册），成功后前端会提示用户设置用户名和密码。此后，用户可选择使用手机号+短信验证码或账号(手机号)+密码登录，注意：用户名不可作为账号登录使用。登录成功后返回访问令牌（`access_token`）和刷新令牌（`refresh_token`），前端将其本地存储，并在后续所有 API 请求头中携带该令牌作为身份鉴权凭证。

**前端（Frontend 动作发起，无 token）**
事件1️⃣ 用户首次登录（注册），前端调用 `POST /api/auth/sms/send` 申请短信验证码。
事件2️⃣ 前端组合 `phone` 与 `sms_code` 调用 `POST /api/auth/login/sms`，等待后端返回。拿到 Token 数据后保存本地，由于是首次登录，前端跳转至设置资料页。
事件3️⃣ 用户设置用户名和密码，前端调用 `POST /api/auth/setup-profile` 提交信息，随后页面路由跳转至控制台。
事件4️⃣ 非首次登录的用户，可直接使用账号(手机号)+密码调用 `POST /api/auth/login/password`，或继续使用短信验证码登录。
事件5️⃣ access_token 临近过期时，前端调用 `POST /api/auth/refresh` 换取新的访问令牌；用户退出登录时调用 `POST /api/auth/logout` 使当前会话失效。

**后端（APM-backend 动作处理，数据中转站）**
事件1️⃣ 接收 `POST /api/auth/sms/send` 验证码请求，生成验证码并调用阿里云短信服务执行发送逻辑，并执行防刷频控，五分钟有效期，返回发送成功状态。
事件2️⃣ 接收 `POST /api/auth/login/sms` 登录请求，在本地数据库 `User` 表中校验手机号和验证码。若校验通过，生成包含用户身份的 JWT Token，将凭证打包返回前端。
事件3️⃣ 接收 `POST /api/auth/setup-profile` 请求，在数据库中为当前用户更新配置好用户名和登录密码。
事件4️⃣ 接收 `POST /api/auth/login/password` 或短信登录请求，在本地数据库校验账户密码或验证码。若校验通过，生成包含用户身份的 JWT Token，将凭证打包返回前端。
事件5️⃣ 接收 `POST /api/auth/refresh` 与 `POST /api/auth/logout`，分别处理登录态续期与会话注销。

## 2. 项目控制台总览

**功能描述：**
用户登录后进入控制台首页，页面自动请求当前用户的项目统计汇总指标，并根据默认筛选项或搜索关键词，请求获取属于本人的所有项目卡片分页列表进行渲染展示。

**前端（Frontend 动作发起，用户已登录有 token）**
事件1️⃣ 进入控制台路由，前端调用 `GET /api/projects/metrics` 获取顶部统计指标数据。
事件2️⃣ 前端调用 `GET /api/projects` 获取项目分页列表数据；若用户使用搜索/筛选操作，则更新翻页参数，重置页码再次调用该列表接口。
事件3️⃣ 用户删除项目时，前端调用 `DELETE /api/projects/{project_id}`，删除成功后刷新项目列表。

**后端（APM-backend 动作处理，数据中转站）**
事件1️⃣ 接收 `GET /api/projects/metrics`，解析当前请求头 token 中的用户身份，在数据库中统计该用户的进行中、已完成项目数及耗时，返回统计载荷
事件2️⃣ 接收 `GET /api/projects` 请求，根据入参中的翻页、搜索条件，在本地查出符合条件的项目，返回结构化的列表数据
事件3️⃣ 接收 `DELETE /api/projects/{project_id}`，先同步通知 Agent-service 清理该项目的对话域数据和知识库数据，再删除本地项目、文件、生成任务、产物、方案版本和操作记录。

## 3. 新建项目、资料上传与发起AI生成

**功能描述：**
用户创建项目容器获取 `project_id` 后，通过获取上传凭证向存储推送实体文件资料。核心资料齐备后，用户触发 AI 生成流程，后端作为中转下发异步解析任务至外部 B-Service 进行文档和计划的解析生成。文档解析服务会将最基础的工序信息传递给后端，后端再转交给 C-Service 进行核心方案的调度计算与初始化。C-Service 会返回多个基准施工方案（Scheme），各服务运算完成并回调后端，后端保存初始的工序表等内容为业务产物，整个生成状态更新完毕。

备注：1. 当前上线版本不支持切换基准施工方案，只以最优方案为基准选为 active 的方案 2.对于C-service 不再提供初始化多方案接口这一点，不是不提供，是当前功能没实现，先不用适配。返回 time_cost也是还没实现

**前端（Frontend 动作发起，用户已登录有 token）**
事件1️⃣ 用户点击创建项目，前端调用 `POST /api/projects` 获得新建的 `project_id`。项目名称后续由 B-Service 解析得出。
事件2️⃣ 用户选定本地文件，分为必选和选传四种类型，每种最多支持上传3个文件（核心文件：招标文件/施工合同支持 `.doc, .docx, .pdf`；选传文件：工程量清单支持 `.xls, .xlsx, .pdf`，CAD 施工图纸支持 `.dwg, .pdf`，其他补充资料支持 `.doc, .docx, .pdf`）。前端调用 `POST /api/projects/{project_id}/files/upload-init`，获得对应文件的物理上传地址。
事件3️⃣ 前端将文件流通过网络推送到拿到的地址，并等待返回成功标识。
事件4️⃣ 前端在物理上传成功后调用 `POST /api/projects/{project_id}/files/complete` 通知后端该文件上传操作就绪。
事件5️⃣ 前端可调用 `GET /api/projects/{project_id}/files` 回显已登记文件；用户移除文件时调用 `DELETE /api/projects/{project_id}/files/{file_id}`。
事件6️⃣ 满足条件后用户点击开始生成，前端调用 `POST /api/projects/{project_id}/generation/start` 发起生成任务，并立刻启动对 `GET /api/projects/{project_id}/generation/status` 的定时轮询，发现状态变为 `succeeded` 后进入工作台。

**后端（APM-backend 动作处理，数据中转站）**
事件1️⃣ 接收 `POST /api/projects`，本地库创建新项目关联此用户，返回 `project_id`。
事件2️⃣ 接收 `upload-init` 请求，在 `ProjectFile` 表落库一条 `pending` 记录并派发一个供上传的链接凭证（目前使用本地静态文件服务，后续不打算更换到阿里云对象存储 OSS了）。
事件3️⃣ 文件流上传由存储服务接收，后端不参与文件流转，只依赖上传成功后的回调通知。
事件4️⃣ 接收 `files/complete`，变更对应文件的状态标识为 `uploaded`，同时将文件可访问的 URL 存储在数据库中，以便后续传给 `agent-service` 与 `b-service`（文档解析服务）。
事件5️⃣ 接收文件列表查询和文件删除请求，返回项目已登记文件或软删除指定文件。
事件6️⃣ 接收 `generation/start`，创建一条状态为 `running` 的生成任务。同时向外部 B-Service (biaoshu) 下发项目信息和文档解析命令和B-Service (schedule-generator) 下发计划基础工序解析任务，得到 base_process_table (基础工序信息表) 后，立即使用该表调用 C-Service 生成 time-cost 数据和多个初始施工方案 (Scheme)。此外，后端将文档类资料传给 Agent-service，触发其针对该 `project_id` 建立基于 chroma_db 的向量知识库。

**详细说明**

- 本地联调可通过 `POST /api/projects/mock` 使用 mock 数据集快速创建项目并物化初始产物，不经过真实文件上传链路。
- 内部回调目前分为 `parse-result`、`document-result`、`graph-result`、`time-cost-result`、`crew-plan-result`。后端会按 `request_id` 做幂等处理，并拒绝已下线的 `schedule/gantt/network` 产物类型，统一使用 `graph`。
- 后端接收回调后会落地为数据库产物记录，等各链路执行状态均到达终点后，将生成任务更新为成功；针对 C-Service 返回的多方案，在数据库为每个方案创建一个 `ProjectScheme` 及对应的初始 `SchemeProcessVersion`。
- Agent-service 应在生成链路中接收项目文档并建立或更新项目知识库，用于后续知识文档查询。

**外部服务（B/C-Service 动作处理）**
事件6️⃣ B-Service 接收文档解析和计划解析任务，生成施工组织设计项目信息元数据、设计文档和基础工序信息表；C-Service 接收基础工序信息表后生成 time-cost 数据和多个初始施工方案，标注最优方案为 `active` 并主动回调。

## 4. 工作台产物查看与切换

**功能描述：**
任务生成成功后，用户进入统一工作台，通过切换上方的各类页签（例如：施工组织设计、网络图、成本等），向后端请求各细分模块下属于该项目最新一代版本的具体产物数据并在前端渲染出图表结构。注意：其中进度计划列表、甘特图、网络图三种视图在前端已合并为一套 `graph` 类型数据，前端拿到此数据后分别渲染。
*注：成果导出功能为纯前端处理逻辑，后端无需提供专门导出接口。*

**前端（Frontend 动作发起，用户已登录有 token）**
事件1️⃣ 用户点击不同的 Tab，前端分别发起特定的获取请求，例如调用 `GET /api/projects/{project_id}/artifacts/document/latest` 或 `.../graph/latest` 或 `.../time-cost/latest` 或 `.../crew-plan/latest` 获取对应分类数据。
事件2️⃣ 上传资料页签或工作台需要汇总信息时，前端调用 `GET /api/projects/{project_id}/workbench/upload-summary` 获取主文件摘要、AI 提取项目信息和已生成产物摘要。

**后端（APM-backend 动作处理，数据中转站）**
事件1️⃣ 接收各种产物查询请求，通过 `project_id` 在库里的对应产物表下检索最近一次生成成功的产物详情，整理后原样返回给前端。
事件2️⃣ 接收工作台汇总请求，聚合项目文件、解析信息、当前产物摘要后返回。

**详细说明**

- 前端接收各接口下发的产物数据后交由业务组件渲染；`graph` 数据包含开始时间、结束时间、工序名字、工种名字、持续时间、工种人数、是否关键路径、排序名 `seqNo`、依赖工序等字段。

## 5. AI 对话与动作调整

**功能描述：**
用户在对话区通过聊天向 AI 发送提问或委托执行动作（如：全局压缩、局部压缩、突发事件应对、或撤销操作）。针对一个具体的 `active` 方案，每一个动作回写后都会生成并保存一个新的 `SchemeProcessVersion`，其中记录了从初始工序到目前的迭代步骤序号、对应的 action 类型，以及该版本的具体工序表数据（用户回退动作如 `revert-local-compression` 也作为一次单独的 action 记录）。

备注：1.撤销操作在上线版本暂不支持，回话切换也暂不支持。当前对话采取第一次回话初始后，前端记住 chat_id，之后均请求此 chat_id. 2.Agent是调用后端提供的action接口，提供用户的操作意图识别和其他必要参数，然后后端统一去构造要传给C服务的所有数据。所有委托去往 C 服务的动作都是必须经过后端的。

**前端（Frontend 动作发起，用户已登录有 token）**
事件1️⃣ 对话页初始化，前端调用 `POST /api/agent/tickets` 申请短期通讯票据 `agent_ticket`。
事件2️⃣ 前端将获取到的 `ticket` 附在请求头中，调用 Agent-service 的初始化、会话创建、消息发送接口，并通过 SSE 订阅本次消息的流式输出。
事件3️⃣ 用户发出提问或调整指令，前端向 Agent 发送内容；若 Agent 返回需要确认，前端把用户“是/否”作为同一会话的下一条消息继续提交。
事件4️⃣ 前端若监听到 Agent 执行了动作，可通过 `GET /api/projects/{project_id}/operations/{operation_id}` 轮询后端正式动作状态；若收到 Agent 的 refetch 信号，则重新抓取最新产物并重绘画布。

**后端（APM-backend 动作处理，数据中转站）**
事件1️⃣ 接收前端申请，签发具有 `agent:chat`、`agent:session:read`、`agent:session:write`、`agent:kb:read`、`agent:kb:write`、`agent:action:invoke` 等作用域的短期 JWT ticket 给前端。
事件2️⃣ Agent-service 使用 ticket 完成会话初始化、会话创建、消息发送和 SSE 流订阅鉴权。
事件3️⃣ 当 Agent 判断用户消息属于正式调度动作时，APM-Backend 作为中介调度真实的 C-Service。在向 C-Service 传递数据时，必须附带当前 scheme 的 `initial_process_version.task_table_json` (最初方案数据)，以及从初始版本到当前版本的所有 action 列表（包含 `action_type` + `action_payload`）。
事件4️⃣ 前端或 Agent 查询动作状态时，后端根据 `AgentOperation` 与其绑定的 `GenerationJob` 同步返回 `accepted/running/succeeded/failed` 等状态、错误信息和结果版本引用。

**外部服务（Agent-service 智能服务与 C-Service 联通）**
事件1️⃣ Agent-service 解析 `ticket`，建立本次对话的访问上下文。
事件2️⃣ Agent-service 创建会话、接收用户消息，并通过 SSE 返回路由、确认、执行进度和最终结果。
事件3️⃣ C-Service 从后端接收原始初始的施工方案以及截止目前累计的所有 action（由自然时间判断完成状态，后端无需考虑现实完成逻辑），重新排布生成新一版施工方案并回调 APM-backend 落库。
事件4️⃣ Agent-service 根据后端操作状态和最新 graph 生成验证结果；前端收到 refetch 信号后重新抓取最新产物。

**详细说明**

- Agent-service 当前按路由节点处理五类意图：项目信息查询、建筑知识查询、全局压缩、局部压缩、突发事件处理。
- 对话支持场景包括信息查询、知识文档查询和调度动作调整；信息查询仅与后端交互获取对应数据，知识文档查询由 Agent-service 在项目对应的 `chroma_db` 向量知识库中执行 RAG 检索回答。
- global_compression全局压缩支持从自然语言中抽取目标完成日期或目标总工期，也支持识别优化范围；用户确认后提交正式动作，验证阶段轮询后端状态并回读最新 graph。
- task_compression局部压缩支持抽取工序名称和目标完成日期；后端可基于最新 graph 将工序名解析为 task_id；验证阶段回读该工序最新完成日期。对用户和 Agent 来说，“单工序压缩 / 局部压缩”就是“希望某个工序提前到某个日期完成”
- unexpected_event突发事件处理先只抽取事件意图和日期并请求用户确认，用户确认后才读取 baseline graph、判断日期范围内受影响工序、提交动作；验证阶段用 baseline graph 和 latest graph 对比生成受影响工序的日期变化。
- mock C-Service 当前支持全局压缩、单工序压缩、突发事件处理三类优化接口，异步回调写回 `graph`、`time_cost`、`crew_plan`，并支持基于传入的最新 `initial_task_table` 计算。
- Agent-service 已提供知识库初始化、文档增删、重建、搜索、状态查询和项目删除清理接口；APM 生成和重新生成链路应自动串联知识库初始化或重建。

## 6. 重新生成

**功能描述：**
在已有资料或补充新资料的基础上，用户手动触发重新生成。project_id不变，系统将新建一次带有批次号的生成任务，再次走一遍向外部服务下发解析运算并等待回调落库的链路。同时，新进入的文档文件会被推送到 Agent-service 重新创建并覆盖该项目之前的向量知识库，系统会保留旧历史记录防止原数据丢失。（todo）

**前端（Frontend 动作发起，用户已登录有 token）**
事件1️⃣ 用户点击重新生成，前端调用 `POST /api/projects/{project_id}/generation/regenerate`
事件2️⃣ 请求通过后，如同新建立项目一般，前端重新挂起针对该项目状态接口的定时轮询机制，直至获取成功标识并刷新全页面

**后端（APM-backend 动作处理，数据中转站）**
事件1️⃣ 接收 `POST .../regenerate`，不是复用或新增一个新版方案（Scheme），而是重新走一遍新建的初始化（包括通知 Agent-service 重建对应 project_id 的 chroma_db 知识库），后续产生一批新的初始施工方案，其中一个方案 active，后续的 action 在其基础上迭代版本。
事件2️⃣ 接收生成状态查询请求，返回当前重新生成任务的执行状态，供前端轮询直到成功或失败。

**详细说明**

- 当前 mock 联调阶段重新生成复用全链路重跑；真实业务阶段可按 `artifact_types` 和 `reason` 演进为局部重算或针对性调度。
